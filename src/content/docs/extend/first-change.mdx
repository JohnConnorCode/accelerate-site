When you have a business idea for a new screen, you need to see how a coding agent turns it into a change you can review. Start with the existing Inventory registration example: Codex or Claude Code can prepare local setup, change one heading and show its checks. You learn the extension path while keeping the first change small enough to inspect.

## Give the agent the first task

Open this repository in Codex or Claude Code and use this brief. The agent prepares the change; you review the result and any setup it still needs.

> Read docs/NORTHSTAR.md, AGENTS.md and docs/contributing/EXTENDING.md. For my local fork experiment, preserve existing work and use a separate branch from published main. Check Git, Node 22.16+ and npm, install the locked dependencies if needed, and start the fictional demo. In src/app/admin/example-inventory/page.tsx, change “This page is registered by a manifest” to “My first workspace extension”. Keep the module disabled by default. Run npm run verify:extensions and git diff --check, then show the exact diff and results. Identify the connected test workspace needed to verify the admin page; keep its setup separate from the credential-free demo. Close servers you start when finished. Follow the repository's required verification before submitting application source. Report implementation, verification, review, merge and deployment as separate facts.

For assigned repository work, ask the agent to use the approved base and isolated worker checkout in the live Feature Board packet instead. The commands below explain local setup and help you interpret what the agent reports.

## Start the app

The agent needs Git, Node.js 22.16 or later and npm. Start from the published main branch for a local experiment.

```bash
node --version
npm --version
git clone https://github.com/JohnConnorCode/accelerate-site.git
cd accelerate-site
git rev-parse HEAD
```

For an assigned Feature Board task, use the approved repository base and exact commit in its live execution packet. Resolve a mismatch before changing code.

Then install and start the app:

```bash
npm ci
npm run dev
```

Run the remaining commands from the cloned repository, where `package.json` lives. `npm ci` installs the versions recorded in the lockfile. `npm run dev` starts the local development server; it does not publish the application.

Open the URL printed by the terminal, then visit `/demo/command-center`. You should see a fictional business workspace. Follow [your first workflow](/docs/start/daily-path) to learn the behavior before changing code. Stop your own server with Control-C when finished.

## Make one small change

The repository includes an Inventory example. Its manifest registers a page and workspace toggle; it does not implement stock storage or automatic reordering.

The agent changes the heading in `src/app/admin/example-inventory/page.tsx` and reads `extensions/example-inventory.module.json` to confirm the owned route. Its `defaultEnabled: false` setting stays unchanged, so the experiment remains opt-in.

The first checks confirm registration consistency and show the intended source edit:

```bash
npm run verify:extensions
git diff --check
git diff -- src/app/admin/example-inventory/page.tsx
```

Review a diff containing only the intended heading change. Module registration stays unchanged when only page text changes; the repository's required application checks still apply before a submitted handoff.

## Turn the example into a real feature

[Add a module](/docs/extend/modules) covers a new manifest and route. A real feature also needs explicit business behavior, validation, authorization, storage if required, and meaningful tests. A manifest does not create those for you.

Keep business writes in the shared domain services so the UI, AI tools, and integrations use the same rules. External effects need approval where required, idempotency, and a truthful result. Read the engineering and tenancy contracts linked from `AGENTS.md` before adding a write path.

Run the affected checks and the repository's required verification before submitting application code. Use one heavy job at a time or CI; do not start parallel builds or copy dependency trees to work around resource limits.

## Keep developing through the backlog

You can simply tell a coding agent: “Pick up work from the backlog and go until
it is completed and committed. Follow protocol.” The repository entrypoint
defines that as a complete execution request. The agent continues its current task or selects eligible interrupted work before
starting a ready card. It uses an isolated worktree, follows the live packet, verifies the result,
commits the exact change and submits evidence for review. Internally this uses
`agent:go`, but you do not need to provide a ticket key or command name.

Run `npm run dev:doctor` to check local readiness and `npm run dev:doctor -- --board` for a read-only board connection check. Pickup, diagnostics, heartbeat and submission reuse the configured private profile across worktrees. An owner-authorized local profile uses the existing named-project configuration. A remote contributor configures project-scoped HTTPS access once through the setup workflow and does not need the owner’s database credentials. Agents never ask you to paste secrets into chat. If a feature checkout has unfinished work, preserve it and start a new session from a clean published-main control checkout.

If an agent runs out of time or credit, its next replacement should be able to
continue from saved source and remaining work. With this release's recovery schema
and project policy enabled, the runner resumes an expired task from its latest
checkpoint, a saved copy of unfinished source. It preserves the previous checkout
so work newer than that copy can still be inspected. Initial pickup and progress
updates save checkpoints; newly created source files need explicit inclusion.

The internal runner handles continuation, selection and claim for the natural-language
request. For explicit diagnostics, `npm run agent:status` and
`npm run agent:show -- --card <key>` remain available; `agent:next` is the
compatibility command for a named card. Follow the live acceptance criteria,
use the emitted commands to renew ownership, and submit named checks and the exact
commit with `agent:complete`. For long checks, the bounded job wrapper keeps
ownership current while the command runs. The [agent handoff guide](https://github.com/JohnConnorCode/accelerate-site/blob/main/docs/contributing/NATURAL-LANGUAGE-AGENT.md#preserve-work-between-agents)
explains source checkpoints and attempt-specific commands.
Submission, review, merge and deployment are separate recorded steps. The full
command contract is in `AGENTS.md` and its linked developer handoff.

Every feature change also updates the organized public guides, product changelog and Command Center descriptions in the same pull request. Keep planned capabilities clearly separate from available behavior. Report new gaps through the live board so the next contributor has a concrete task and verification criteria.

**Next:** [Add a module](/docs/extend/modules). If something failed, use [Troubleshooting](/docs/start/troubleshooting).

## Keep agent work within machine capacity

The shared resource runner allows one heavy job at a time across worktrees. An optional [local machine supervisor](https://github.com/JohnConnorCode/accelerate-site/blob/main/scripts/supervisor/README.md) adds a queue and process identity checks for registered agent sessions. It starts off and requires no service credentials. It is separate from Feature Board assignment: continue using the ordinary backlog runner to claim and complete work.

The supervisor can pause a registered producer without terminating it, preserve a paused session during recovery, and report unmanaged launch paths. It does not install hooks into every agent, reconstruct lost conversations, or provide OS-level isolation. Its guide explains configuration, recovery, and the tested limits.

## What to check

If dependencies or registration checks fail, ask the agent to report the failed command and repair the cause before continuing. For an unavailable admin page, check the connected test workspace, administrator access and module enablement. Keep fictional-demo exploration, rendered admin verification and production publication distinct in the handoff.
