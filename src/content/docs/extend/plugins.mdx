A plugin adds business-specific behavior to Command Center using the shared workspace records and services, and it never gets a side door around the approval flow to do it: a focused report, a reviewed operation, or part of a larger business workspace all still play by the same rules as everything else. Explore the [eleven bundled examples](/docs/plugins) to choose a pattern before working through this technical reference.

Runtime plugins declare their tools, triggers, required capabilities and permissions. Registration begins in review; enablement makes approved capabilities available to a workspace. Modules describe the pages, navigation and configuration that present a capability. The [extension overview](/docs/extend) explains how these pieces fit together.

## Build beyond the default workflows

A plugin can be part of an App with custom records, its own lifecycle and a dedicated interface. Use the existing module, entity and domain service paths to implement those capabilities; the runtime manifest alone does not create them. [App design](/docs/extend/apps) explains the choices, and [custom work](/docs/extend/work-primitives) shows how a native queue can retain authoritative state without copying it into a task.

Source-built Apps can change the whole operating experience. The current isolated plugin hosts expose bounded capabilities; adding a new execution capability requires a host implementation and verification. [AI authoring](/docs/extend/ai-authoring) distinguishes source development today from the planned in-app builder.

## Manifest shape

Required: `pluginKey`, `name`, `description`. Optional: version, author, homepage, required capabilities, permissions, config schema, MCP server URL, tools, triggers.

Each tool declares `toolName`, `label`, `description`, input schema, impact (`read`, `internal_write`, `external_action`), whether confirmation is required, and an autonomy level (`prohibited`, `always_ask`, `ask_until_trusted`, `standing_permission`, `autonomous`).

## What still applies

Plugin tools flow through the autonomy policy engine. Mutating tools still stage into `action_queue`. MCP tools discovered from an external server must be registered as `plugin_tools` before use; they do not bypass Accelerate governance. Isolate execution (QuickJS) is the host for untrusted plugin code, with measured bounds. A plugin does not get a raw database handle.

## What not to do

Do not treat a plugin as a way to skip approval. Do not document a plugin as autonomous if its policy is `always_ask`. Do not load plugin code from the `extensions/` JSON directory; that directory is data.

## Document the plugin before release

Every plugin needs an operator guide covering setup, configuration, permissions,
costs, a worked example, disabling, recovery and verified limitations. Bundled
plugins keep `plugins/<id>/README.md` and a public `docsUrl` in their manifest.
`npm run verify:extensions` rejects missing guides and documentation links.
Runtime/MCP submissions supply the same documentation in their review packet;
the current runtime registry does not enforce a documentation field.

Follow the [plugin documentation contract](https://github.com/JohnConnorCode/accelerate-site/blob/main/docs/contracts/PLUGIN-DOCUMENTATION.md).
A reviewer must follow the task against the current implementation; structural
checks cannot establish that the guide is accurate. See the
[Collections guide](/docs/outreach/collections)
for a business workspace and the
[Radar guide](/docs/intelligence/opportunity-radar)
for its daily review workspace, source-backed relationship context, model budgets and current release limits.
