When client feedback arrives in several threads, somebody has to find the latest revision, work out who is reviewing it and chase the missing decision. A proposed Creative Review App could keep those details together, so your team spends less time reconstructing status before doing the next piece of work.

You can ask a coding agent to build this kind of App from the open-source repository today. It can reuse customer records, workspace access and existing business services, which reduces the setup and repeated implementation needed for each custom workflow. You supply the business rules and review a working result; the agent writes the source, registers the extension and runs the checks.

<Callout type="info" title="Start with one repetitive task">
  Describe the work your team repeats, the information they gather and the result the next person
  needs. A useful first App removes a specific round of searching, copying or status chasing.
</Callout>

## Decide what the App should do

For a client review queue, the owner specifies who submits work, who reviews it, which revision a decision applies to and what happens after changes are requested. A useful result shows the current revision, reviewer and outstanding decision together, with the customer history available from the same workspace.

The agent chooses the implementation from those rules. Depending on the workflow, it may need a dedicated screen, new records, a provider connection or an AI tool. Shared customer identity and access checks give it a starting point, while the parts unique to your process still need implementation and verification.

## Review what work it saves

Ask the agent to walk through one complete example, from submission to a recorded decision and the next person's view. Check whether somebody can find the current revision and take the next step without copying status between tools. If the team still has to maintain a parallel spreadsheet, explain the missing step so the agent can address it in the same workflow.

The handoff should include a working preview, setup instructions, the source changes and named check results. Review the business behavior yourself, and have the technical review confirm permissions, saved records and recovery before release.

## Planned: create and update Apps inside Command Center

The intended experience is:

1. Describe an App or a change to an existing App, with relevant business context.
2. Generate a draft in an isolated development workspace.
3. Preview the working interface with fictional or explicitly scoped data on desktop and mobile.
4. Inspect its source, dependency changes, requested capabilities and data migrations.
5. Run checks for business behavior, permissions, replay, failures and the user interface.
6. Review and publish the exact verified App version.
7. Reopen that version for further changes, compare versions and roll back compatible code when needed.

The current source extension path and bounded plugin runtime provide parts of that foundation. The complete in-app authoring flow remains planned.

## What an App can become

An App can add custom records, work types, connections to other systems and a dedicated interface. The agent can contribute its records to supported shared views or implement a workspace designed around the business process. [App design](/docs/extend/apps), [custom work](/docs/extend/work-primitives) and [custom UI](/docs/extend/custom-ui) explain these implementation choices.

A planned development terminal would need an isolated execution environment, scoped access to connections and secrets, resource limits and an inspectable result.

## What to check

Creative Review is a proposed extension, not a bundled App. Use an external coding agent and the repository's source-development workflow today; treat the general-purpose in-app App builder and development terminal as planned.

Bind source, dependencies, requested access, any database changes and check results to the exact version reviewed. Preserve customer identities and execution history across updates, and verify recovery using the documented release workflow.

Check external-action receipts before telling someone that a message or business operation completed. Plan recovery for database changes and completed external actions separately from restoring an earlier code version.
