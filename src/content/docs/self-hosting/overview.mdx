Two paths exist. The fictional demo needs no credentials. A connected workspace needs a Supabase project you control, then one owner account. Do not point a fork at someone else's database, Vercel project, provider accounts, or customer records. Version-specific detail lives in `docs/self-hosting/SELF-HOSTING.md` in your checkout.

## Explore with no credentials

You need Git, Node.js 22 or later, and npm 10 or later.

```bash
git clone https://github.com/JohnConnorCode/accelerate-site.git
cd accelerate-site
npm ci
npm run dev
```

Open the local URL printed in the terminal, then visit `/demo/command-center`. Choose a fictional business. This path does not create records in your database and does not need Resend, OpenRouter, or Google.

## Connect a workspace you control

### 1. Create the local environment

```bash
cp .env.example .env.local
```

Keep `.env.local` out of Git. Fill in values from a **new** Supabase project:

| Variable                                               | Purpose                                                         |
| ------------------------------------------------------ | --------------------------------------------------------------- |
| `NEXT_PUBLIC_SITE_URL`                                 | Application origin, including the local port                    |
| `NEXT_PUBLIC_SUPABASE_URL`                             | Project URL                                                     |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY`                        | Public anon / publishable key                                   |
| `SUPABASE_SERVICE_ROLE_KEY`                            | Server-only key; never prefix this with `NEXT_PUBLIC_`          |
| `SUPABASE_PROJECT_REF`                                 | Project ref you intend to migrate                               |
| `SUPABASE_DB_HOST`, `SUPABASE_DB_PORT`, `SUPABASE_DB_USER`, `SUPABASE_DB_PASSWORD` | Session-mode pooler connection for migrations |
| `ADMIN_EMAIL`                                          | Owner email you will sign in with                               |

Uncomment the `BOOTSTRAP_*` identity fields in `.env.example` and set your business name, domain, site URL, and founder email **before** the first migration. Otherwise the seed can keep the reference deployment's identity.

Leave `RESEND_*`, `OPENROUTER_*`, `GOOGLE_*`, and `CALENDLY_*` unset until a later workflow needs them.

### 2. Apply the database

Install PostgreSQL client tools so `psql` is available. Confirm the printed project ref and database host before you continue.

```bash
npm run db:migrate:all
npm run db:verify-schema
npm run verify:bootstrap-identity
```

`db:migrate:all` applies every file in `scripts/lib/migration-manifest.mjs` in order. Migrations are additive and idempotent; re-running after a fix is safe. To apply one file, use `npm run db:migrate -- <path>`. Do not edit a recorded migration to force replay.

### 3. Configure authentication

In the Supabase project, enable email authentication. Set the site URL and the `/auth/callback` redirect. For `http://localhost:3000`, the callback is `http://localhost:3000/auth/callback`. Create the Auth user whose email exactly matches `ADMIN_EMAIL`. Tenant operators need active membership in the selected workspace; platform administration stays limited to that founder identity.

### 4. Sign in and check Setup Center

Restart `npm run dev` after editing environment files. Sign in at `/admin`. The heading is **Sign in to operations**.

Open **Setup Center** at `/admin/setup`. Core schema and founder access should read ready. Open **Tenant operations** at `/admin/tenants` if the shell signs you in but shows no workspace.

Then run [your first result](/docs/start/first-value) with a fictional lead.

## Add providers later

Start without external effects. Add one capability at a time, then prove it with a receipt, not with a saved key:

- **Resend** for outbound email and signed delivery webhooks.
- **OpenRouter** at the tenant level for AI workloads.
- **Google Workspace OAuth** for Gmail, Calendar, and selected Drive folders.
- **Calendly** only when its optional attribution path is required.
- **Plausible** only when external analytics are desired; first-party analytics is built in.

Provider configuration is not readiness. Setup Center says so in its subtitle: every status reflects this deployment, and secrets are never displayed. Use the matching verification command in `docs/self-hosting/SELF-HOSTING.md` after each connection.

## Recover common failures

- **Connect your Supabase project** on the login screen: `NEXT_PUBLIC_SUPABASE_URL` or the anon key is missing. Set them, restart the server, retry `/admin`.
- Migration command refuses to run: `SUPABASE_DB_HOST` is unset or points at the wrong region pooler. There is no default host.
- `verify:bootstrap-identity` still shows Accelerate's brand: set `BOOTSTRAP_*` and re-run the identity check. Changing those variables later does not rewrite an existing workspace; use Branding / tenant configuration for later edits.
- Sign-in succeeds, admin routes fail: the Auth email does not match `ADMIN_EMAIL`, or membership is missing. Fix membership on **Tenant operations**. Do not weaken authentication to hide that.
- Schema check fails: re-run `npm run db:migrate:all`, then `npm run db:verify-schema`. Do not paste SQL from memory out of order.

Before real customer data, follow the verification sequence in `docs/self-hosting/SELF-HOSTING.md`, including tenant isolation with fictional workspaces. A working local demo does not establish production readiness.
