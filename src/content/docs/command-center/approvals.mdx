When AI prepares a customer reply or a workflow proposes several tasks, review the exact change before it runs. Approvals keeps that decision connected to its context and recorded result. Eligible actions can earn a proposed increase in autonomy, which a person reviews separately.

## What an approval is

AI tools and connected integrations that propose a change stage it here rather than running it immediately: an email draft, a suggested pipeline move, a task change, a prepared reminder. A read-only question, like asking the assistant to summarize a deal, never creates an approval, because nothing about it changes a record.

A manual action you take yourself is different and does not route through this queue at all. Writing and sending a reply in [Conversations](/docs/conversations/reply) uses that screen's own composer and confirmation step; it does not need a second AI proposal stacked on top of something you already decided to do.

## Reviewing one

1. Open **Today → Needs your decision** or **Work → Approvals**, and select a pending item.
2. Read the proposed action and the context behind it. For a message, that means the actual recipient and the actual wording, not just the fact that a message exists.
3. Choose the decision that matches what you want.

| Decision            | What happens                                                                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Approve             | The action runs as shown. Approving an email proposal can put a message in front of a real customer, not just mark a draft as read.                        |
| Save draft to Gmail | For a `create_gmail_draft` proposal, saves the exact reviewed reply as an editable Gmail draft. It is not sent; review, edit, and send it in Gmail Drafts. |
| Revise              | The proposal goes back to whatever produced it, AI or workflow, so you can change it and review the new version before deciding again.                     |
| Reject              | The action does not run. Give a reason when the screen offers one; it is what the system learns from.                                                      |

Gmail follow-ups stay in **Work → Follow-ups** after the draft is saved. Open the draft there, then send it manually from Gmail when it is ready. Gmail sync records the sent message and keeps the follow-up open while waiting for a reply. A matching reply closes that loop; the reply itself remains available in Conversations for any new work. If sync is stale or the provider result is uncertain, the item remains open for reconciliation rather than being silently closed or retried.

Draft access is optional in **Setup → Gmail draft access**. Google’s `gmail.compose` scope technically permits sending too, but this follow-up action calls Gmail’s draft-creation method only. It never calls a send method. See Google’s [draft creation reference](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/create) and [OAuth scope list](https://developers.google.com/workspace/gmail/api/auth/scopes) for the provider-level distinction.

Approving and the action succeeding are two different events. A provider outage can leave an approved send unfinished, so check the result afterward rather than assuming approval was the last step. [Receipts and audit](/docs/start/receipts) covers the exact statuses to look for.

## How approval turns into autonomy

An autonomy policy sets how a particular action is allowed to run. New policies default to `always_ask`, which requires review. An action configured as `ask_until_trusted` can become eligible for a proposed promotion when its executed approvals meet the current threshold of three approvals over at least seven days, subject to the policy checks.

A person confirms any promotion. Eligible actions may then use `standing_permission`, which authorizes work within its recorded constraints while preserving an audit history. Repeating an approval never grants a new permission by itself, and changing the permission’s scope or constraints requires renewed review.

Hard safety floors remain in force for account deletion, credential changes, deletion of financial history, customer-database exports, high-value refunds and major financial transfers. The reversibility rules also keep sending an email, activating a campaign and sending an invoice behind a human decision. Check the policy for the specific action instead of assuming that another action’s approval history applies.

## When a standing permission changes

A permission belongs to one workspace and either one coworker or the workspace-wide action. Repeating registration updates that same scope. Changing its level, constraints or source clears the previous approval; changing only its label or description keeps the decision. Restoring standing permission requires an explicit human approver. Hard safety floors remain in force, including floors set for the whole workspace.

If an older installation reports multiple matching policies when saving approval, have the workspace administrator apply the current migration catalog and retry the supported policy operation. The recovery keeps existing policy IDs and creation dates, records the before-and-after decision in the audit, and leaves other workspaces and coworker scopes untouched. Unknown constraints still require review even after a standing permission is saved.

## Undoing an executed task write

Creating, updating, reopening or deleting a task in the workspace runs through the same executor as any programmatic write, so every save leaves a claim, an authorization entry and an audit receipt. When the action is reversible, the prior state is captured at execution: the created row, the previous field values including the description, or the full deleted row.

An executed reversible action can be undone exactly once, restoring that captured state. A second undo is refused rather than re-applied. Irreversible effects, such as a sent email or an activated campaign, can never be undone; only a human approval runs them in the first place.

## What to check

- An external assistant connected through MCP cannot approve its own staged proposal. Its own confirmation prompt is not the same thing as your approval inside Command Center, and the action still waits here regardless of what it told you.
- Do not assume repeated approvals have quietly removed a gate on their own; check the current autonomy setting for that action type if you are unsure whether it still needs your review.
- If an approved action's outcome is unclear, inspect [Activity](/docs/command-center/activity) and the action's own result before creating a second attempt. Retrying blind risks a duplicate send.
